## (a) Refactoring & dead code elimination

### Audit findings

This codebase is unusually clean for a dead-code audit. No dedicated tooling exists yet (`knip`, `depcheck`, `ts-prune`, `madge` are absent from `package.json`'s devDependencies — confirmed via `grep -i "knip\|depcheck\|ts-prune\|madge" package.json`, no output), but the manual sweep still turned up only a handful of real findings:

1. **`Graph3D`'s `hdr`/`theme` constructor options are effectively dead state — verified first-hand, not just by the audit agent.** `src/core/Graph3D.js:51,55,70` documents them as constructor options with a usage example implying they auto-apply (`new Graph3D({ canvas, pixelRatio: 2, hdr: '/env/studio.hdr', theme: 'studio-dark' })`). They're stored as plain instance fields at `Graph3D.js:178-179` (`this.hdr = hdr; this.theme = theme;`) and read back only inside `serialize()`/`deserialize()` (`Graph3D.js:571-572,616-617`). But `createScene(name)` (`Graph3D.js:425-438`) constructs `new GraphScene({ graph3d: this, name })` without ever passing `this.hdr`/`this.theme` through, and `GraphScene.js` never reads `graph3d.hdr`/`graph3d.theme` back off the reference it's given — confirmed via `grep -n "graph3d\.\(hdr\|theme\)" src/scene/GraphScene.js`, zero matches. **A user following the documented constructor example gets no HDR and no theme applied to any scene they create.** The only way to actually apply either is `scene.environment.setHDR(url)` / `scene.applyTheme(name)` directly, per scene, after `createScene()`.

2. **`examples/24-GraphHTML-test/` is a real, working example orphaned from site navigation.** Confirmed via `grep -rn "24-GraphHTML"` across every `.js/.json/.md/.mjs` file — zero hits outside its own directory, unlike `examples/23-live-trading/`, which is linked from three separate places (`site/concepts/scale.md:77`, `site/playground.md:36`, `site/recipes/live-stream.md:44`). **Resolved as part of this session's documentation work** — the new [`site/recipes/graphhtml-custom-labels.md`](site/recipes/graphhtml-custom-labels.md) now links to it, matching the convention every other recipe follows.

3. **`.claude/TODO.md:23-32`'s "build fails" entry is stale.** It describes a Rollup multi-chunk/`output.file` error. `npm run build` was run live during this audit and succeeds cleanly in ~4s (`dist/graph3d.esm.js`, `.esm.min.js`, `.umd.js`, only a non-fatal warning — see finding (d.1) below). This TODO item should be marked resolved or deleted; it's stale documentation, not a real build problem.

4. **`src/material/text/SDFText.js:8-11`'s doc comment is stale in the same way.** It says the bundled MSDF atlas ("`roboto-msdf.png`/`.json`") "has not been generated yet" as of Prompt 108. Both files exist on disk today (`src/material/text/assets/roboto-msdf.{png,json}`, 74KB + 85KB, confirmed via `ls -la`) and `SDFText.create()` works — verified live in this session's earlier GraphHTML alignment-bug fix, which rendered real SDF text in a browser. Cosmetic-only: update the comment, no functional issue.

5. **No commented-out code, no genuine `TODO`/`FIXME`/`deprecated` markers, no unreferenced source files.** A basename cross-reference across all 226 non-test files in `src/` found zero files unreferenced anywhere else in `src/`, `examples/`, `site/`, or `tests/`. The 3 hits for "legacy"-adjacent grep patterns are all in `SDFText.js` referencing `.claude/TODO.md` by name, not deprecation markers. `.gitignore`/`dist/`/build config show no drift — single `rollup.config.js`, no competing bundler config, no stale `.eslintrc*` alongside the flat `eslint.config.js`.

6. **CLAUDE.md §1.4 mandates `madge --circular src/` stay clean, but nothing enforces it.** No `package.json` script runs it, and it isn't in any CI config found in the repo. This isn't a finding of an actual circular import (not checked in this pass) — it's a policy-vs-enforcement gap worth closing while touching build tooling anyway.

### Proposed design/fix

- Either (i) wire `hdr`/`theme` constructor options through to `createScene()` so every scene created after construction picks them up automatically (matches the documented example), or (ii) remove the options and the misleading JSDoc/example entirely and point users at `scene.environment.setHDR()`/`scene.applyTheme()` (matches the new [HDRI recipe](site/recipes/custom-hdri-environment.md) this session added). **Recommendation: (ii).** Per-scene HDR/theme application is already a clean, well-tested, documented path (`GraphSceneEnvironment.setHDR`, `GraphScene.applyTheme`) — auto-applying a single constructor-level HDR/theme to *every* scene a multi-scene `Graph3D` instance creates is a worse default than explicit per-scene control, and building it now would be scope creep beyond "fix the dead code."
- Delete the two stale doc/comment items (TODO.md's resolved build-failure entry, SDFText.js's stale atlas-missing comment).
- Add a `madge:circular` script and wire it into whatever CI exists (or note its absence as a separate, smaller finding if there's genuinely no CI yet — this plan doesn't assume one).

## (b) Coordinate mapping fix

### Audit findings — root cause, traced first-hand

**The bug: `Axis` centers its tick labels on a band scale's band, but `BarChart`/`HeatmapChart` never do the same for the data they render, so labels and bars/cells are offset by exactly half a band-width.**

Evidence, in the order that establishes the mismatch:

1. **`scale.band()`'s own contract**: `src/compose/scale/band.js:7-8`'s JSDoc states plainly — "`scale(value)` returns a band's start edge; `scale.bandwidth()` returns its width." Confirmed in the implementation: `band.js:34-36`'s `scale(value)` delegates straight to the underlying ordinal scale with no centering. This is correct, intentional, D3-parity behavior — the scale itself is not the bug.

2. **`Axis.js` correctly compensates for this.** `src/compose/axis/Axis.js:288`: `const bandOffset = typeof this.#scaleValue.bandwidth === 'function' ? this.#scaleValue.bandwidth() / 2 : 0;` — then every tick's position (`Axis.js:291`) and every label's position (`Axis.js:305`) is computed as `this.#scaleValue(value) + bandOffset`, i.e. the true center of the band.

3. **`generator.bar()` never does the same.** `src/compose/generator/bar.js:71`: `position: [x, (y + baseline) / 2, 0]` — `x` is used directly as the bar mesh's position with no offset. A `THREE.Mesh`/instanced-object's `position` is the geometry's own center (bar geometries are centered-at-origin boxes), so a bar positioned at `x = scale(category)` (the band's *left edge*, per finding 1) renders shifted left by `bandwidth()/2` from where it should visually sit.

4. **`generator.heatmap()` has the identical gap.** `src/compose/generator/heatmap.js:78`: `return { position: [x, y, z], scale: [size, size, size] };` — same raw, uncompensated position. `HeatmapChart`'s own JSDoc example (`src/chart/HeatmapChart.js:33-34`) uses `scale.band()` for both `x` and `z` directly, so every default heatmap-cell layout hits this.

5. **The wiring that connects a chart's `.x(fn, scale)` call to the generator confirms there is no compensation anywhere in the pipeline.** `src/chart/GraphChart.js:1462-1464` calls `this.#generator.x(resolveAxisAccessor(this.#xField))` (and the same for `y`/`z`). `resolveAxisAccessor` (`src/chart/axisField.js:44-47`) is: `return scale ? (d, i) => scale(fieldAccessor(d, i)) : fieldAccessor;` — a bare `scale(value)` call, no `bandwidth()` anywhere. **`grep -rn "bandwidth" src/` returns exactly one hit outside `band.js`'s own definition: `Axis.js:288`.** No chart-side code compensates.

6. **Blast radius, confirmed by grep, not guessed:** only `BarChart` and `HeatmapChart` reference `scale.band()`/`generator.bar`/`generator.heatmap` (`grep -ln "generator.bar\|generator\.point\|scale\.band\|band()" src/chart/*.js`). `ScatterChart`'s earlier match was a false positive (`generator\.` alone, not `band`-related — reconfirmed via a targeted re-grep with zero hits). `NetworkChart`/`TreeChart`/`PackChart`/`PieChart` position data via force/hierarchy/angle layouts, not `.x(fn, scale)` fields, so they're structurally unaffected. **Point scales (`scale.point()`) are unaffected regardless of chart type** — `point()` fixes `paddingInner` to `1`, which makes `bandwidth() === 0` always (`band.js:126-134`), so the missing offset is a no-op there. Only *padded band scales* — the default categorical axis every `BarChart`/`HeatmapChart` example in this codebase actually uses — show the visible misalignment.

7. **Zero existing tests pin the buggy behavior.** Checked `tests/chart/BarChart.test.js` and `tests/chart/HeatmapChart.test.js` for any `.x(fn, scale.band()...)` combined with a `position.x` assertion: every `.x()` call in both files is accessor-only, no scale attached (`grep -n "\.x(" tests/chart/BarChart.test.js` / `tests/chart/HeatmapChart.test.js` — confirmed, none pass a scale). The only band-scale usage in the test suite is in `tests/integration/BarChart.test.js:16` and `tests/integration/HeatmapChart.test.js:15-16`, and neither asserts an exact position value against it. **The fix will not require updating any existing test assertion — only adding new ones.**

### Proposed design

Extract the offset math Axis.js already has into a shared helper, and use it in **both** places rather than leaving two independent inline implementations of the same rule (CLAUDE.md §1.1's two-strike DRY rule: Axis.js is the first caller, the chart pipeline is the second — this is exactly the case that rule exists for).

- New file: `src/compose/scale/bandCenter.js`, exporting `bandCenter(scale)`: `return typeof scale?.bandwidth === 'function' ? scale.bandwidth() / 2 : 0;` — one pure function, no THREE dependency, lives in the layer that already owns scale math (CLAUDE.md §1.4's `compose/` row). Re-exported from `compose/scale/index.js`.
- `Axis.js:288` becomes `const bandOffset = bandCenter(this.#scaleValue);` — behavior-preserving, verified by the existing Axis test suite passing unchanged.
- `chart/axisField.js`'s `resolveAxisAccessor` becomes: `return scale ? (d, i) => scale(fieldAccessor(d, i)) + bandCenter(scale) : fieldAccessor;` — this is the actual bug fix. Applying it unconditionally (not gated per chart type) is deliberate: it's a no-op for every non-band scale (continuous scales have no `.bandwidth`; point scales have `bandwidth() === 0`), so it only changes behavior exactly where the bug exists, and it matches the D3 idiom every categorical-axis tutorial teaches (`x(d.category) + x.bandwidth() / 2`) without requiring every chart author to remember to add it by hand.

## (c) Labeling system API redesign

**Depends on (b).** The redesign below assumes `bandCenter()` exists and both `Axis` and the chart data pipeline agree on where "the center of a datum" is — building a positioning API on top of the pre-fix math would just relocate the bug into the new API's surface.

### Audit findings — three independent implementations of the same thing

There is no single "label" primitive in this codebase today. Text ends up on screen via **three separately-implemented code paths** that duplicate the same core logic (load/build SDF text, recenter it on an anchor point, billboard it toward the camera every frame, dispose it later) with three different levels of correctness and three different public shapes:

1. **`SDFText`** (`src/material/text/SDFText.js`) — the actual GPU-text primitive. Clean, well-designed, disposal-contract-compliant (`dispose()` at `SDFText.js:332-337`). Exposes `.mesh`, `.width`, `.height`, and — since this session's earlier bug fix — `.centerOffset` (`SDFText.js:318-321`, `{x: -width/2, y: height/2}`). This is the one piece that's genuinely reusable and shouldn't change.

2. **`Axis`'s own private `#renderTextLabels`** (`Axis.js:326-365`) — builds real `SDFText` meshes for tick labels *by hand*: calls `SDFText.create()` directly, applies `text.centerOffset` itself (`Axis.js:354`), wraps the result in a raw `GraphMesh` (`Axis.js:346-351`), and maintains its **own private billboard loop** (`Axis.js:359-364`, `this.#billboardTick`, a `loop.add()`/`loop.remove()` pair private to the `Axis` instance). It never calls `graphHTML` — despite `graphHTML`'s SDFText-fallback path (below) doing the *exact same sequence of operations*.

3. **`graphHTML`'s SDFText fallback path** (`src/material/text/GraphHTML.js:294-310`) — calls `SDFText.create()`, applies `sdfText.centerOffset` (`GraphHTML.js:310`), and its own `finalize()` (`GraphHTML.js:247-264`) does its own scene-add + its own billboard loop (`GraphHTML.js:254-257`, a *second, independent* `loop.add()`/`loop.remove()` pair) + its own manual disposal (`GraphHTML.js:258-261`: `scene.remove(mesh); disposeFn();` — hand-rolled, not delegated to `GraphMesh.dispose()`, even though `object/GraphMesh` exists precisely to own this pattern).

Three consequences, all evidence-backed:

- **The billboarding loop callback is implemented twice** (`Axis.js:360-363` and `GraphHTML.js:254-256`) — nearly identical code (`mesh.quaternion.copy(camera.quaternion)` on every tick), never factored out, despite both being registered on the exact same shared `loop` singleton.
- **`graphHTML()`'s returned handle is a plain object, not a `GraphObject`/`GraphMesh`.** `GraphHTML.js:233-245` builds `{ type: 'graphHTML', mesh, isExperimental, ready, dispose() }` by hand — it does not extend or wrap `GraphObject` (`src/object/GraphObject.js`), so it gets none of the registry/disposal-contract infrastructure every other renderable in this codebase gets for free, and per `.claude/TODO.md:161-168` (read directly in this audit), `graphHTML()` has **no `.update()` method at all** — a label's text/position/style cannot be changed after creation; the only option is dispose-and-recreate.
- **No integration with `Selection`/the data join.** Every other per-datum visual concern in this library (`.attr()`, `.style()`, `.color()`, `.opacity()`) goes through `Selection`'s uniform `meshes`/`instanced` backend abstraction (`src/compose/selection/`). Labels don't — `graphHTML()` takes one target at a time and returns one handle at a time; a chart with 500 labeled bars needs 500 individually-tracked handles with no bulk update, bulk dispose, or join-driven enter/update/exit lifecycle. `annotation.label()` (`src/compose/annotation/label.js`) is thinner still: a plain object with a hand-rolled `on`/`emit` pair (`label.js:75-88`, explicitly *not* reusing `interact/eventEmitter.js`'s existing implementation because of the layering rule described in its own comment at lines 28-37 — a legitimate constraint, not a mistake, but it means yet another one-off event registry exists in the codebase for the same `on`/`emit` shape).

This is exactly the situation CLAUDE.md §1.1's DRY rule (and its two-strike corollary) is written for, except it's now a *third* occurrence, not a second — and it's precisely why "labeling system API redesign" was scoped as its own initiative rather than a drive-by fix.

### Proposed design

A new `compose/label` module — same layer, same sanctioned `object/` carve-out `compose/selection`/`compose/axis`/`compose/annotation` already use (CLAUDE.md §1.4's `compose/` row) — providing one chainable, disposable, Selection-compatible primitive that every current label producer (`Axis`, `annotation.label`, `graphHTML`, and any future chart-level `.labels()` API) is rewritten to call instead of hand-rolling SDF text + billboarding + disposal a third and fourth time.

**Public shape** (sketch, not final signatures — that's implementation-time detail):

```js
import { label } from 'graph3d.js'; // new top-level export, compose/label

// Single label, chainable configuration, matches this codebase's existing
// fluent-setter idiom (GraphAnim, Selection, generator.bar(), ...):
const l = label()
  .text('42%')
  .position({ x: 1, y: 2, z: 0 })
  .font({ size: 0.3, color: '#ffffff' })        // typography
  .anchor('center')                              // positioning — reuses bandCenter()-style math from (b)
  .billboard(camera)                              // opt-in, shares ONE loop registration across every label instance, not one per label
  .render(scene);

l.text('88%');      // update — the missing piece graphHTML never got
l.dispose();         // real GraphMesh disposal, not a hand-rolled scene.remove() + geometry.dispose()

// Bulk form, Selection-compatible — the piece nothing today provides:
chart.selection().labels((d) => `${d.value}%`, { font: { size: 0.25 }, anchor: 'center' });
```

- **Typography**: `fontSize`, `color`, `align`, `letterSpacing`, `outline`, `glow` — the exact option set `SDFText.create()` already accepts (`SDFText.js:350-357`), surfaced through the new API's `.font()` rather than re-invented.
- **Color**: reuses `compose/color`/`compose/palette` the same way `.style('color', fn)` already does on `Selection` — no second color-resolution path.

## (d) Production readiness

### Audit findings

1. **HIGH — the UMD build is broken for real `<script>`-tag consumers using PostFX or thick lines.** `rollup.config.js`'s UMD output only maps `three` itself to a global (`globals: { three: 'THREE' }`) — confirmed directly by reading the config. The build's own console warning (visible on every `npm run build`, verified live) lists 17 unmapped `three/addons/...`/`three/examples/jsm/...` submodules (`UnrealBloomPass`, `EffectComposer`, `SSAOPass`, `Line2`, `LineMaterial`, etc.). A consumer loading `dist/graph3d.umd.js` via a plain `<script>` tag (the entire reason a UMD build exists) gets a `ReferenceError` the instant any code path touching PostFX or thick lines executes, because the UMD wrapper looks up e.g. `window.UnrealBloomPass_js`, which doesn't exist. Silent for ESM/bundler consumers (they resolve real imports), real for the UMD `<script>`-tag use case.

2. **MEDIUM — disposal tests don't literally follow CLAUDE.md §3.4's own stated leak-test contract.** The policy: "creates and disposes the class N times (default 1000) and asserts `renderer.info.memory.geometries` and `.textures` return to baseline." A repo-wide grep for `info.memory`/`renderer.info` inside `tests/integration/*-disposal.test.js` (13 files exist, covering `Axis`, `GraphChart`, `GraphInstancedObject`, `GraphMesh`, `GraphObject`, `GraphObjectLoader`, `GraphObjectMaterial`, `GraphScene`, `GraphSceneCamera`, `GraphSceneClipping`, `GraphSceneEnvironment`, `GraphSceneLight`, `GraphSceneShadows`) returns **zero matches**. They use `vi.fn()` spy assertions and structural checks (`scene.children.length === 0`) instead — arguably more deterministic than polling a real memory counter, but it's a real, citable gap between stated policy and actual practice. Only 2 of the 13 files actually run the "N=1000" loop the policy describes. Separately: 13 files under `src/material/presets/*.js` create GPU materials with **no dedicated disposal test file** at all — traced and found to be stateless factory functions whose disposal is delegated to (and covered by) `GraphObjectMaterial`'s own tests, so likely not a real gap, but worth a second pair of eyes given the volume.

3. **MEDIUM — `FrameBudget`'s diagnostic payload is always empty in production.** `src/core/Graph3D.js:193` calls `this.#frameBudget.record(deltaSec * 1000)` — a single argument. `FrameBudget.record`'s real signature (`src/core/FrameBudget.js:110-115`) is `record(frameMs, { chartId = null, drawCalls = 0, triangleCount = 0, meshCount = 0 } = {})` — every `graph3d:slow-frame` event this library ever emits in real use carries `drawCalls: 0, triangleCount: 0, meshCount: 0, chartId: null`, regardless of what's actually happening on screen. The feature exists, is wired into the tick loop, and is completely half-built — a developer debugging a real slow-frame issue gets an event telling them *that* something is slow but nothing about *what*.

4. **LOW-MEDIUM — `vitest.config.js`'s coverage thresholds undershoot CLAUDE.md's own stated policy.** CLAUDE.md §4 (Definition of Done) states "Coverage thresholds (lines ≥85, branches ≥80, functions ≥85) are not regressed." `vitest.config.js:30-33` configures only `{ lines: 80, branches: 80 }` — no `functions` threshold at all, and `lines` is 5 points under the stated policy. Doc/config drift, not a live quality problem (the suite is 100% green at 3246/3246 tests), but worth reconciling one way or the other — either the policy document is aspirational and should say so, or the config should catch up to it.

5. **Positive findings, stated for completeness rather than omitted:** WebGL context-loss handling is real and tested (`src/core/Graph3DRenderer.js:159-160,239-240`, covered by `tests/core/Graph3DRenderer.test.js` and `tests/integration/phase1.test.js:121-157`). No confirmed memory leaks anywhere — every one of the 33 `loop.add()` call sites in `src/` pairs correctly with a `loop.remove()` in the owning class's `dispose()`, including non-obvious cases like `GraphChart.js`'s LOD tick handler. ### Proposed design/fix

- **UMD fix**: either (i) add the missing `output.globals` entries mapping every `three/addons/...` submodule to sensible global names (fragile — depends on consumers also loading those as separate globals, which is unusual for `three/addons`), or (ii) document that the UMD build is only supported for the core feature set (no PostFX, no `Line2`-based thick lines) and have PostFX/`GraphObjectLoader`'s thick-line features throw a clear, actionable error when accessed from a UMD-loaded build instead of a cryptic `ReferenceError`, or (iii) stop shipping `three/addons` imports in code paths reachable from the UMD entry at all (split PostFX into a separate optional UMD-incompatible bundle). **Recommendation: start with (ii)** — it's the smallest change that turns a confusing runtime crash into an honest, actionable error, and it doesn't require guessing at global names that may not match what a real `<script>`-tag consumer actually loads.
- **Disposal test policy**: reconcile CLAUDE.md §3.4's wording with what the test suite actually does. The spy-based approach is arguably better engineering (deterministic, no flaky memory-counter polling across GC timing) — if that's the real intent, **update CLAUDE.md §3.4 to describe the spy-based pattern as the standard**, rather than silently leaving a stated policy nothing follows. If the `renderer.info.memory` check is considered non-negotiable, add it to the 2 files that already run it and to the other 11.
- **FrameBudget fix**: pass real `{ drawCalls, triangleCount, meshCount }` from `renderer.info.render`/`.memory` at the `Graph3D.js:193` call site — the data is already available on the renderer, it's just not being read.
- **Coverage thresholds**: bump `vitest.config.js` to match CLAUDE.md's stated 85/80/85 (or lower the stated policy to match reality — pick one, don't leave them disagreeing).
